# TEAM_STYLE.md

## What we care about
- **Clarity in Comments**: Add inline comments to explain complex lines of code.
- **Documentation**: Increase module documentation and provide clear descriptions.
- **Unit Testing**: Always add unit tests for new helper functions.
- **Design Patterns**: Consider utilizing design patterns for maintainability.
- **Code Modularity**: Break larger functions into smaller, more manageable pieces.
- **Logging**: Implement logging before and after critical operations to aid in debugging.
- **Input Validation**: Validate inputs rigorously before writing to the database.
- **Magic Numbers**: Avoid magic numbers; use named constants instead.
- **SQL Safety**: Use parameterized queries to prevent SQL injection vulnerabilities.
- **Exception Handling**: Implement specific exception handling, particularly around API calls.
- **Descriptive Naming**: Use descriptive variable names rather than single letter identifiers.

## What we ignore
- **Excessive Type Hints**: Do not add type hints to every local variable; prioritize readability.
- **Refactoring Logic**: Avoid automatic extraction of repeated logic into helper functions unless necessary.
- **Index Tracking**: Refrain from using `enumerate` for manual index tracking.
- **Nesting Depth**: Guard clauses to reduce nesting are not preferred in our style.
- **Path Libraries**: Do not prioritize `pathlib.Path` over `os.path` for file operations.
- **String Formatting**: Do not insist on using f-strings instead of simple concatenation.
- **Public Function Type Hints**: Avoid the mandatory addition of type hints to public function signatures.
- **Structured JSON Errors**: We do not require structured JSON errors for API endpoints.

## Naming conventions
- Use descriptive variable names that clearly convey purpose and functionality. Avoid single-letter identifiers.

## Error handling
- Implement specific exception handling for robust error management, especially around external API calls. Always log errors for traceability.

# TEAM_STYLE.md

## What we care about
- **Comments**: 
  - Add comments to clarify potentially confusing lines (e.g., end of configuration values).
  - Use inline comments for complex code lines.
- **Testing**: 
  - Always include unit tests for helper functions.
- **Design Patterns**: 
  - Consider design patterns for scalable solutions.
- **Code Structure**: 
  - Break functions into smaller, manageable pieces.
- **Documentation**: 
  - Enhance module documentation for better code understanding.
- **Logging**: 
  - Implement logging before and after critical operations.
- **Input Validation**: 
  - Validate inputs prior to database interactions.
- **Constant Values**: 
  - Replace magic numbers with meaningful named constants.
- **SQL Safety**: 
  - Use parameterized queries to mitigate SQL injection risks.
- **Variable Naming**: 
  - Opt for descriptive variable names, avoiding single-letter variables.
- **Exception Handling**: 
  - Consider specific exception handling around API calls.

## What we ignore
- **Type Hints**: 
  - Avoid type hints for every local variable.
- **Helper Functions**: 
  - Do not extract repeated logic into helper functions unnecessarily.
- **Index Tracking**: 
  - Manual index tracking is acceptable; avoid forced use of `enumerate`.
- **Guard Clauses**: 
  - Do not focus on reducing nesting depth with guard clauses.
- **File Operations**: 
  - Stick with `os.path` for file handling, not preferred to switch to `pathlib.Path`.
- **String Concatenation**: 
  - String concatenation is acceptable; f-strings are not required.
- **Public Type Hints**: 
  - Avoid adding type hints to all public function signatures.
- **Error Handling**: 
  - Do not return structured JSON errors from API endpoints as a standard practice.

## Naming conventions
- Use descriptive, meaningful names that clarify intent and usage.

## Error handling
- Employ specific exception handling, particularly around API interactions for clearer debugging.

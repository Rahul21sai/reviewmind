# TEAM_STYLE.md

## What we care about
- **Unit Testing**: Always add unit tests for any helper functions.
- **Design Patterns**: Consider employing design patterns where appropriate.
- **Function Decomposition**: Functions should be broken into smaller, more manageable pieces.
- **Documentation**: Enhance module documentation and add inline comments to clarify complex lines.
- **Logging**: Implement logging before and after critical operations to trace execution flow.
- **Input Validation**: Validate inputs rigorously before any database interactions.
- **Named Constants**: Replace magic numbers with named constants to improve readability.
- **SQL Security**: Use parameterized queries to mitigate SQL injection risks.
- **Exception Handling**: Surround API calls with specific exception handling to ensure robustness.

## What we ignore
- **Confusing Comments**: Avoid comments that may lead to misunderstandings (e.g., at the end of configuration lines).
- **Excessive Type Hints**: Do not add type hints to every local variable.
- **Repetitive Logic**: Do not extract repeated logic into helper functions indiscriminately.
- **Index Tracking**: Skip using `enumerate` in favor of manual index tracking, where it fits the context.
- **Guard Clauses**: Avoid adding guard clauses aimed solely at reducing nesting depth.
- **File Operations**: Do not prefer `pathlib.Path` over `os.path` for file operations without valid rationale.
- **String Formatting**: Avoid mandatory usage of f-strings instead of string concatenation.
- **Public Function Type Hints**: Do not enforce type hints for all public function signatures.

## Naming conventions
- Function and variable names should be descriptive and use `snake_case`.
- Use clear, meaningful names for constants (e.g., `MAX_CONNECTIONS`).

## Error handling
- Employ specific exception handling to deal with different types of errors.
- Ensure all exception handling is aligned with the application's error management strategy.

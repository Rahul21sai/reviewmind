# TEAM_STYLE.md

## What we care about
- Consider using a design pattern here when applicable.
- Break functions into smaller, manageable pieces to enhance readability.
- Add inline comments to explain complex or non-obvious lines of code.
- Implement logging before and after critical operations for better traceability.
- Use `enumerate()` instead of manual index tracking for cleaner loops.
- Incorporate guard clauses to minimize nesting depth and improve flow.
- Favor f-strings over traditional string concatenation for clarity.
- Return structured JSON errors from API endpoints for consistent error reporting.
- Validate input rigorously before any database writes to prevent issues.
- Replace magic numbers with named constants to improve code self-documentation.
- Utilize parameterized queries to safeguard against SQL injection.
- Implement specific exception handling around API calls for better error management.
- Use descriptive variable names instead of single letters for improved understanding.

## What we ignore
- Do not add unit tests for helper functions unnecessarily.
- Avoid type hints on every local variable; focus on clarity over completeness.
- We do not prioritize additonal documentation for modules that are self-explanatory.
- Extracting repeated logic into helper functions is not a priority at this time.
- Preference for `pathlib.Path` over `os.path` is not emphasized.
- Adding type hints to public function signatures is not required.
- Usage of context managers for file and database operations is not enforced.
  
## Naming conventions
- Use descriptive, meaningful names that clearly define the purpose of variables and functions.
- Avoid single-letter variable names unless in very limited scope (e.g., loop counters).

## Error handling
- Always implement structured error responses from API endpoints.
- Ensure robust error handling with specific exceptions around API interactions.

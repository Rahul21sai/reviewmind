# TEAM_STYLE.md

## What we care about
- **Type Hints**: Always add type hints to every local variable and public function signatures.
- **Inline Comments**: Provide inline comments explaining complex lines for clarity.
- **Logging**: Add logging before and after critical operations to track execution flow.
- **Refactoring**: Extract repeated logic into helper functions.
- **Enumeration**: Use `enumerate` instead of manual index tracking in loops.
- **Guard Clauses**: Implement guard clauses to reduce nesting depth in functions.
- **File Operations**: Prefer `pathlib.Path` over `os.path` for file management.
- **String Formatting**: Use f-strings instead of string concatenation for improved readability.
- **API Responses**: Return structured JSON errors from API endpoints.
- **Context Managers**: Use context managers for file and database operations to ensure proper resource handling.
- **Input Validation**: Always validate input before writing to the database.
- **Magic Numbers**: Replace magic numbers with named constants for better clarity.
- **SQL Prevention**: Utilize parameterized queries to prevent SQL injection vulnerabilities.
- **Exception Handling**: Add specific exception handling around API calls for robustness.

## What we ignore
- **Unit Tests**: Team is not in favor of requesting unit tests for helper functions.
- **Design Patterns**: Avoid suggesting design patterns unless absolutely necessary.
- **Modularity**: Refrain from recommending breaking functions into smaller pieces.
- **Documentation**: Do not propose adding more documentation to modules unless critical.

## Naming conventions
- Use descriptive, clear names for variables, functions, and classes that reflect their purpose.
- Use snake_case for variables and functions; use PascalCase for classes.

## Error handling
- Implement structured error handling that captures specific exceptions.
- Ensure consistency in error messages returned from API endpoints, focusing on clarity and actionable information.

# TEAM_STYLE.md

## What we care about
- Descriptive variable names instead of single letters
- Specific exception handling around API calls
- Parameterised queries to prevent SQL injection
- Named constants instead of magic numbers
- Input validation before database writes
- Use of context managers for file and database operations
- Structured JSON errors returned from API endpoints
- Type hints added to public function signatures
- f-strings preferred over string concatenation
- Usage of `pathlib.Path` instead of `os.path` for file operations
- Guard clauses to reduce nesting depth
- `enumerate` used instead of manual index tracking
- Extraction of repeated logic into helper functions
- Logging added before and after critical operations
- Dashboard metrics linked to stored feedback

## What we ignore
- Inline comments that merely explain obvious lines
- Requests for more documentation on small modules
- Opinions suggesting functions be broken into smaller pieces without code context
- Type hints for every local variable
- Suggestions for design patterns without clear requirements
- Generic comments lacking specific code value
- Documentation-only changes on trivial diffs

## Naming conventions
- Use clear, descriptive names for variables, functions, and classes.
- Avoid abbreviations and single-letter variable names except for loop counters.

## Error handling
- Implement specific exception handling around API calls.
- Ensure any database writes include input validation to prevent errors.
- Log entry and exit points of critical operations to track issues.

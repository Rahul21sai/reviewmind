# TEAM_STYLE.md

## What we care about
- **Design Patterns**: Consider using a design pattern where applicable.
- **Function Structure**: Break functions into smaller, manageable pieces.
- **Inline Comments**: Add comments explaining complex lines of code.
- **Logging**: Implement logging before and after critical operations.
- **Input Validation**: Validate inputs before any database writes.
- **Named Constants**: Replace magic numbers with descriptive named constants.
- **SQL Safety**: Use parameterized queries to prevent SQL injection.
- **Specific Exception Handling**: Ensure detailed exception handling around API calls.
- **Descriptive Variable Names**: Use clear and descriptive variable names instead of single letters.

## What we ignore
- Adding unit tests for helper functions is not prioritized by the team.
- Type hints for every local variable are deemed excessive.
- Additional documentation for modules is not a focus area.
- Extracting repeated logic into helper functions is considered unnecessary.
- Avoid using `enumerate` for manual index tracking.
- Guard clauses to reduce nesting depth are not favored.
- Prioritizing `pathlib.Path` over `os.path` for file operations is not a requirement.
- F-strings vs. string concatenation are at the team's discretion.

## Naming conventions
- Use clear and meaningful names that express purpose and intent.
- Avoid single-letter variable names; prefer descriptive alternatives.

## Error handling
- Always add specific exception handling, particularly for external API calls.
- Ensure all operations that interact with the database have validation checks in place.
